Under the hood

How this works

The published architecture, and how it ended up running on a static website.

Dual neural networks

A user network maps 14 per-genre preference features to a 32-d embedding v_u; an item network maps 16 movie content features (year, average rating, 14 genre flags) to v_m — both 256 → 128 → 32 with ReLU, L2-normalised. The predicted rating is their dot product. Because both live in the same space, distances between movie embeddings also give "similar movies" for free — that's what the nearest-neighbour line under each result shows.

Training

Trained by minimising squared error over ~50,000 observed MovieLens ratings, with regularisation against overfitting on sparse user–item data, optimised with Adam:

J = Σ ( v_u(j) · v_m(i) − y(i,j) )² + λ‖θ‖²

Targets were min-max scaled to [−1, 1]; features standardised — the demo applies the exact same scalers.

Static-site deployment

GitHub Pages can't run Python — so the item embeddings for all 847 movies were precomputed offline with the trained item network, and the (small) user network's weights were exported to JSON. At click-time, JavaScript standardises your profile, runs three matmuls, and takes 847 dot products. Total model payload: ~1 MB. This mirrors the paper's retrieval-and-ranking argument: precompute what's expensive, compute per-user what's cheap.

Evaluation

In the paper, the approach was evaluated on MovieLens across 20 repeated runs against collaborative, hybrid, classification-based, and knowledge-based baselines — leading on all three metrics.
